Add experimental Convex support for Email SDK workflows at `@opencoredev/convex-email/workflows`. A new `workflowRuns` table with revision-checked `workflows:*` functions backs `convexWorkflowStore`, `convexWorkflowScheduler` uses `ctx.scheduler.runAt` for waits, and `convexWorkflowEmail` sends each step through the new `ConvexEmail.sendWorkflowStep` and `workflows:enqueueSend`. That mutation records each send in a new `workflowSends` table, keyed by the step's idempotency key, in the same transaction that queues the email, so a replayed step never queues a second email, even after `cleanupAfterDays` deleted the first. Records are kept while the run is active and for the new `workflowSendRetentionDays` config option (default 30) after it finishes; a send that lands after its run ended starts that clock at once. Workflow emails are deduped only through `workflowSends`, so a caller's `send` with the same idempotency key never becomes a workflow's send, and the reverse. The resume function `convexWorkflowScheduler` calls takes `{ runId, owner? }` and should call `engine.resume(runId, { owner })`, so lease-expiry jobs left by earlier claims stop instead of re-arming. Ordinary sends are unchanged. Using workflows requires `@opencoredev/email-sdk` 3.1 or later for `createWorkflowEngine`. The entry imports only types from `@opencoredev/email-sdk/workflows`, so the component's peer range stays `^3.0.1` and apps that don't use workflows can stay on 3.0.x.
