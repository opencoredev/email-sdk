<Callout type="warn" title="Experimental">
`@opencoredev/convex-email/workflows` builds on the experimental [email workflows](/docs/guides/email-workflows) API and may change in a minor release. It needs `@opencoredev/email-sdk` 3.1 or later.
</Callout>

The component provides everything a workflow engine needs on Convex:

- `convexWorkflowStore` keeps runs in the component's `workflowRuns` table. Saves check the run's revision inside one mutation, so two actions racing on a run can't overwrite each other, and only the action holding the run's lease executes its steps. Subject lookups page through the table 100 runs per query, so an `unsubscribed` event reaches every run for that subject.
- `convexWorkflowScheduler` schedules each wait with `ctx.scheduler.runAt`.
- `convexWorkflowEmail` sends each `ctx.send` through the component queue with the step's idempotency key. Workflow emails get the same retries, fallback, webhook status, and test mode as any other email, and a replayed step finds the email it already queued instead of adding a second one.

## Define the engine and its actions

The engine runs inside actions, because your workflow code lives in your app. Define the workflow anywhere in `convex/`, then wire one action per entry point:

```ts title="convex/onboarding.ts"
import { ConvexEmail } from "@opencoredev/convex-email";
import {
  convexWorkflowEmail,
  convexWorkflowScheduler,
  convexWorkflowStore,
} from "@opencoredev/convex-email/workflows";
import { createWorkflowEngine } from "@opencoredev/email-sdk/workflows";
import { v } from "convex/values";
import { components, internal } from "./_generated/api";
import { internalAction, type ActionCtx } from "./_generated/server";
import { onboarding } from "./workflows/onboarding";

const email = new ConvexEmail(components.convexEmail, {
  adapters: [{ kind: "resend" }],
  defaultAdapter: "resend",
});

function engine(ctx: ActionCtx) {
  return createWorkflowEngine({
    email: convexWorkflowEmail(email, ctx),
    store: convexWorkflowStore(components.convexEmail, ctx),
    scheduler: convexWorkflowScheduler(ctx, internal.onboarding.resume),
    workflows: [onboarding],
  });
}

export const start = internalAction({
  args: { userId: v.string(), email: v.string(), name: v.string() },
  handler: async (ctx, args) => {
    await engine(ctx).start(onboarding, args, { id: `onboarding:${args.userId}`, subject: args.email });
  },
});

export const resume = internalAction({
  args: { runId: v.string() },
  handler: async (ctx, { runId }) => {
    await engine(ctx).resume(runId);
  },
});

export const sendEvent = internalAction({
  args: { name: v.string(), subject: v.string() },
  handler: async (ctx, args) => {
    await engine(ctx).sendEvent(args);
  },
});

export const resumeDue = internalAction({
  args: {},
  handler: async (ctx) => {
    await engine(ctx).resumeDue();
  },
});
```

Start a run from a mutation with `ctx.scheduler.runAfter(0, internal.onboarding.start, { ... })`, and send `activated` or `unsubscribed` events the same way.

## Recover crashed runs

Add a cron for `resumeDue`. A Convex action that fails mid-step is not retried, so the cron picks the run up again once its five-minute lease expires:

```ts title="convex/crons.ts"
import { cronJobs } from "convex/server";
import { internal } from "./_generated/api";

const crons = cronJobs();

crons.interval("resume email workflows", { minutes: 5 }, internal.onboarding.resumeDue, {});

export default crons;
```

## What the queue can't carry

The component stores messages as JSON, so two message features are rejected before anything is queued, and the run fails without retrying:

- `sendAt`. Use `ctx.sleepUntil` before the send instead.
- Binary attachment content (`Uint8Array`, `ArrayBuffer`, `Blob`) and `path` attachments. Pass base64 strings with `contentEncoding: "base64"`.

`ctx.send` returns `{ adapter: "convex-email", id }`, where `id` is the component email id. Delivery happens later in the component's worker, so read its status with `email.status` as usual.
