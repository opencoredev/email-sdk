**Short answer:** Pick Resend for a small, modern outbound API with React Email templates and a fast first send. Pick Mailgun when you need per-message metadata or its mature routing and inbound parsing. Both support CC, BCC, custom headers, attachments, tags and scheduled sending, so Email SDK's field checks pass a Resend-to-Mailgun fallback for any message, and Mailgun-to-Resend for messages without metadata or repeated header names. Falling back after a failed request also needs onUnknownDelivery: "continue", which can send a duplicate.

Mailgun was one of the original developer email APIs and it still shows: flexible routing, inbound parsing, EU and US regions, and a message API that supports everything in the unified shape — CC, BCC, headers, attachments, tags, metadata, and scheduled delivery. It is a strong pick when you need inbound mail or regional data residency alongside outbound sends. Resend is younger and more focused: outbound transactional email with a polished developer experience, React Email templates, and a simpler pricing page, but no per-message metadata field. If your application round-trips structured data on every message, Mailgun's metadata support matters; if your priority is shipping the first send this afternoon, Resend's onboarding is hard to beat, and the SDK keeps a later migration to a single-line change.

## Same code, either provider

With Email SDK the send call is identical for both providers. Only the adapter import changes:

```ts
import { createEmailClient } from "@opencoredev/email-sdk";
import { resend } from "@opencoredev/email-sdk/resend";

const client = createEmailClient({
  adapters: [resend({ apiKey: process.env.RESEND_API_KEY! })],
});

await client.send({
  from: "hello@yourdomain.com",
  to: "user@example.com",
  subject: "Welcome!",
  html: "<p>It works.</p>",
});
```

Or run both, with automatic fallback:

```ts
import { createEmailClient } from "@opencoredev/email-sdk";
import { resend } from "@opencoredev/email-sdk/resend";
import { mailgun } from "@opencoredev/email-sdk/mailgun";

const client = createEmailClient({
  adapters: [
    resend({ apiKey: process.env.RESEND_API_KEY! }),
    mailgun({ apiKey: process.env.MAILGUN_API_KEY!, domain: "mg.yourdomain.com" }),
  ],
  defaultAdapter: "resend",
  fallback: { adapters: ["mailgun"] },
});
```

## FAQ

### Should I use Resend or Mailgun?

Pick Resend for a small, modern outbound API with React Email templates and a fast first send. Pick Mailgun when you need per-message metadata or its mature routing and inbound parsing. Both support CC, BCC, custom headers, attachments, tags and scheduled sending, so Email SDK's field checks pass a Resend-to-Mailgun fallback for any message, and Mailgun-to-Resend for messages without metadata or repeated header names. Falling back after a failed request also needs onUnknownDelivery: "continue", which can send a duplicate.

### Can I switch from Resend to Mailgun without rewriting my email code?

Yes. With Email SDK both providers share one typed send() call and one message shape, so switching from Resend to Mailgun is a one-line adapter change plus an API key. The SDK fails fast if a message uses a field Mailgun does not support, so nothing is silently dropped.

### Which message fields does Resend support that Mailgun doesn't?

Mailgun supports every message field that Resend supports, so nothing is lost moving a message from Resend to Mailgun.

### Can I use Mailgun as a fallback for Resend?

Partially. Email SDK checks field support before every send: a fallback is rejected from Mailgun to Resend for messages using Metadata, repeated header names. Messages that avoid those pass the field checks. A failed send still falls back only when the SDK knows the first provider didn't send it, unless you set onUnknownDelivery: "continue". Adapter limits also apply. Mailgun: Native personalized delivery caps one request at 1,000 recipients. Mailgun: Tag names are discarded; tag values are sent as o:tag values.
